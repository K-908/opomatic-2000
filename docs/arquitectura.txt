ARQUITECTURA TÉCNICA DE OPOMATIC-2000
OBJETIVO DE LA MIGRACIÓN; NÚCLEO HTTP Y ACCESO MYSQL IMPLEMENTADOS

1. PROPÓSITO

Conservar las funciones y el contrato HTTP de OpoMatic-3000 con una pila que
pueda ejecutarse en un hosting compartido tradicional. El frontend sigue siendo
React 19, TypeScript y Vite. El backend será PHP y la persistencia MySQL. No se
utilizarán contenedores ni procesos de larga duración controlados por el usuario.

La versión .NET sigue en el repositorio hermano. Esta versión parte de una base
vacía, por decisión del propietario; no se trasladan datos de SQLite.

2. COMPONENTES

Navegador -> HTTPS/Apache -> React estático y /api -> PHP -> PDO -> MySQL

- `frontend/`: copia del frontend React. Produce `dist/` mediante Vite. Las rutas
  de la SPA necesitan fallback a `index.html` al refrescar.
- `backend/public/`: contiene el punto de entrada PHP y router de desarrollo.
  `/health` ya responde; la infraestructura enruta rutas `/api/*`, cuyos
  controladores funcionales siguen pendientes.
- `backend/src/Http/`: enrutamiento, lectura de JSON, respuestas, Problem
  Details y rutas de autenticación preparados; validaciones de negocio pendientes.
- `backend/src/Application/`: casos de uso de temas, preguntas, importación,
  generación, entrega, historial, estadísticas y cuentas.
- `backend/src/Domain/`: reglas puras, incluida la puntuación en un solo lugar.
- `backend/src/Infrastructure/`: conexión PDO, repositorios iniciales,
  transacciones, sesiones PHP, cookies y límite de login implementados; tokens
  de test pendientes.
- `backend/tests/`: pruebas de núcleo HTTP y acceso MySQL implementadas;
  pruebas funcionales pendientes.
- `database/schema.sql`: esquema inicial para importar en una base vacía.

En producción, React y PHP deben compartir el mismo origen para que la cookie
de sesión se envíe sin CORS. `VITE_API_BASE_URL=/` se fija al compilar; Vite
inserta esta variable en el paquete estático. En desarrollo se configurará un
proxy de Vite o una URL local para PHP.

3. CONTRATO Y SEGURIDAD

La API debe mantener las rutas, estados y cuerpos JSON de
`docs/diseno-api.txt`. Los errores siguen el formato `application/problem+json`.
Toda entrada se valida en PHP. Los contratos de red se separan de las tablas.

Las cuentas `Gogloglo` y `Virginia` se guardarán en `Users`, con hashes creados
por `password_hash()` y verificados por `password_verify()`. Los hashes .NET
anteriores no se reutilizan porque se parte de una base vacía. El alta inicial
ya dispone de un comando PHP CLI explícito y transaccional que rechaza una
segunda ejecución; el esquema no contiene contraseñas. Falta ejecutar el
comando con las contraseñas definitivas en el hosting.
Las sesiones usan cookies HttpOnly, Secure en HTTPS y SameSite=Lax, con
caducidad absoluta de doce horas. React envía `X-CSRF-Token` leído de una
cookie separada para cambios de estado. Los intentos de login se limitan a
cinco por IP y minuto y los mensajes no revelan si existe la cuenta. Las
sesiones y el limitador se guardan en un directorio privado escribible.

El token temporal de un test debe estar firmado o autenticado, incluir usuario
y caducidad, y no revelar las respuestas correctas. La entrega se verifica en
servidor y se guarda transaccionalmente. `submissionId` impide duplicados.

Las credenciales MySQL y la clave de firma se configuran fuera de Git. Nunca
deben publicarse `src/`, `vendor/`, `.env` ni copias de seguridad. La forma de
subir archivos depende del hosting y se definirá al conocer su document root.

4. BASE DE DATOS

MySQL 8.0.16+ con InnoDB y `utf8mb4`; la compatibilidad con MariaDB deberá
verificarse en la versión concreta del hosting. PDO usa consultas preparadas.
Las fechas se guardan en UTC. Las importaciones y entregas usan transacciones.
Los intentos guardan snapshots de temas, preguntas y opciones para preservar
el histórico. La nota `Score` se guarda como entero en millonésimas, conforme
al esquema, y se convierte al formato del contrato HTTP en el backend.

Las modificaciones futuras del esquema se versionarán con scripts incrementales
y una guía de aplicación; `schema.sql` representa la instalación inicial.

5. VERIFICACIÓN

El frontend copiado debe superar lint, pruebas unitarias y build. La futura API
debe probar respuestas HTTP, autenticación, importación transaccional,
restricciones reales de MySQL, idempotencia, puntuación e historial. Una prueba
E2E deberá recorrer login, creación/importación, test, entrega y estadísticas
en un entorno aislado antes de publicar.
